1.1. Abstract
This document specifies the integration-test tier of X Paradox X's testing pyramid
(008_game_testing.txt Section 1.7), exercising two or more engine modules together to prove
that unit-verified behaviors compose correctly across module boundaries.

1.2. Key Words
integration test, module boundary, turn cycle, cross-module behavior, fixture, pytest.

1.3. Executive Summary
Where 009_game_unit_tests.txt proves each engine module correct in isolation, this document
proves that combinations of modules — turn engine driving movement/combat/territory engines,
card engine driving upgrade/territory engines, victory engine driving persistence — behave
correctly together, using the same seeded, deterministic fixtures established at the unit
tier.

1.4. Key Findings
1.4.1. Integration tests operate on at least two modules from 006_game_scaffolding.txt
Section 1.6 per test case, distinguishing them from the single-module scope of
009_game_unit_tests.txt.
1.4.2. A full turn cycle (Draw -> Income -> Move -> Action -> End Turn) is the primary
integration surface and must be exercised end-to-end at the module level, short of full UI
involvement (that is covered by 013_game_end2end_testing.txt).
1.4.3. Combat resolution feeding into territory capture, and territory capture feeding into
income and Dominion Points, are the two most consequential cross-module chains and receive
dedicated test coverage.
1.4.4. The AI Adviser's read of serialized game state and its recommendation's subsequent
re-validation through the rules engine (016_game_modes.txt Section 1.7.3.2) is treated as an
integration concern, not a unit concern, since it spans the adviser service and the rules
engine.
1.4.5. Integration tests reuse the seeded RNG fixtures from 009_game_unit_tests.txt Section
1.6.9 rather than redefining new randomness handling.

1.5. Philosophical Preamble
A correct set of parts does not guarantee a correct machine. Integration tests exist because
the rules engine's authority (003_game_philosophy.txt Section 1.6.1) is only real if its
modules actually agree with each other once wired together, not merely each individually
correct in a vacuum.

1.6. Integration Test Scope

1.6.1. Turn-Cycle Integration
A full turn (Draw, Income, Move, Action, End Turn) executed end-to-end at the module level
produces the exact combination of state changes expected across the turn engine, movement
engine, and event log, per 017_game_rules.txt Section 1.8.

1.6.2. Combat-to-Territory Integration
A combat that reduces a defending piece to 0 HP on a territory tile results in that
territory's ownership transferring to the attacker in the same turn, per 017_game_rules.txt
Sections 1.7.3 and 1.9.1.

1.6.3. Card-to-Engine Integration
Playing a card of a given suit/rank correctly invokes the corresponding engine action (e.g. a
Spades card invoking the combat engine, a Diamonds card invoking the territory/credit
engine), per 017_game_rules.txt Section 1.10.

1.6.4. Upgrade-to-Income Integration
Purchasing a Market upgrade via a Bishop increases that territory's income in the next Income
phase; purchasing a Fortress increases the defending occupant's effective Defence in the next
combat on that tile, per 017_game_rules.txt Section 1.9.3.

1.6.5. Victory-to-Persistence Integration
Reaching a victory condition correctly locks further state mutation (009_game_unit_tests.txt
Section 1.6.10) and correctly persists the final match outcome for statistics
(010_game_player_statistics.txt Section 1.6).

1.6.6. AI Adviser Integration
A serialized game-state summary produces an Adviser recommendation that, when re-validated
through the rules engine, is confirmed legal; an intentionally stale/invalid state summary is
correctly rejected rather than silently accepted, per 016_game_modes.txt Section 1.7.3.

1.7. Test Environment and Fixtures
1.7.1. Integration tests run against an in-memory instantiation of the full module set from
006_game_scaffolding.txt Section 1.6, with no external network dependency (the AI Adviser
integration test uses the deterministic heuristic fallback per 016_game_modes.txt Section
1.7.4, not a live external service).
1.7.2. Fixtures construct a minimal board (4x4, per 017_game_rules.txt Section 1.6.1) by
default to keep integration tests fast, reserving larger board sizes for
012_game_perfomance_tests.txt.

1.12. Conclusion
Six cross-module integration-test scopes give X Paradox X confidence that its correctly
unit-tested engines also cooperate correctly, ahead of full end-to-end validation in
013_game_end2end_testing.txt.
