1.1. Abstract
This document specifies the unit-test scope, conventions, and required cases for the
X Paradox X backend, implementing the 100% coverage/100% pass-rate baseline established in
008_game_testing.txt at the finest-grained testing tier.

1.2. Key Words
unit test, pytest, movement legality, combat resolution, turn phase, seeded randomness,
debug panel, coverage.

1.3. Executive Summary
Unit tests exercise each engine module in `src/game` and `src/data` (per
006_game_scaffolding.txt) in isolation, using `pytest`, with a seeded random-number service
so dice and card outcomes are deterministic and repeatable. Ten required test categories are
enumerated below, directly carried forward from the testing checklist in the original
ideation session, mapped onto the specific mechanics defined in 017_game_rules.txt.

1.4. Key Findings
1.4.1. Every rules-engine module listed in 006_game_scaffolding.txt Section 1.6 requires a
corresponding unit-test module before it is considered complete, per
005_game_coding_standards.txt Section 1.9.
1.4.2. Combat and card-resolution tests require the seeded RNG service (see
019_game_data_structures_algorithms.txt) to assert exact, reproducible outcomes rather than
statistical approximations.
1.4.3. Illegal-action tests (diagonal-only-piece moving orthogonally, acting outside the
Action phase, playing a card without a valid target, purchasing an upgrade without
sufficient credits, acting after victory) must assert that game state is left byte-for-byte
unchanged, not merely that an error is raised.
1.4.4. A development-only debug panel (Section 1.7) is required to directly trigger each of
the three victory conditions and to manipulate state for test setup, without being reachable
in a production build.
1.4.5. Unit tests do not cross module boundaries (e.g. a movement-legality test does not
also assert territory-income side effects); cross-module behavior is covered in
011_game_integration_tests.txt.

1.5. Philosophical Preamble
A unit test is the smallest unit of trust the rules engine can offer: it isolates one claim
("this move is legal," "this combat resolves to this outcome") and proves it independent of
everything else. Ten required categories below exist because each corresponds to one place
where an untested rule would silently become a broken promise to the player
(008_game_testing.txt Section 1.5).

1.6. Unit Test Scope by Module

1.6.1. Movement Legality
Legal movement per piece type and real chess movement rules (017_game_rules.txt Section
1.7.1); illegal movement (off-board, through an occupied/impassable tile, wrong direction
for the piece type) leaves state unchanged.

1.6.2. Combat Resolution
Attacker-wins, tie, and defender-wins outcomes per the dice-resolution table
(017_game_rules.txt Section 1.7.3), using a fixed seed to assert exact HP deltas and piece
removal at 0 HP.

1.6.3. Turn-Phase Enforcement
Draw and Income cannot be skipped; Move and Action can be skipped; actions attempted outside
their designated phase are rejected without state mutation, per 017_game_rules.txt Section
1.8.

1.6.4. Territory Capture and Income
Neutral-territory capture by occupation; opposing-territory capture by defeat or
undefended occupation; income calculation (1 credit per owned territory per turn); Dominion
Point accrual after three consecutive held turns, per 017_game_rules.txt Section 1.9.

1.6.5. Card Resolution
Every suit/rank combination resolves to the correct class and magnitude tier per
017_game_rules.txt Sections 1.10.2-1.10.3, including the Ace wild-choice case; playing a
card with no valid target is rejected without state mutation.

1.6.6. Upgrade Purchase
Only a Bishop may purchase an upgrade (017_game_rules.txt Section 1.7.4); each of Fortress,
Market, and Relay applies its documented effect; a second upgrade on an already-upgraded
territory is rejected.

1.6.7. Victory Evaluation
Territory-majority, King-capture, and Dominion-Points-threshold victories each independently
trigger correctly per 017_game_rules.txt Section 1.11; no false-positive victory triggers on
partial progress.

1.6.8. Persistence
Save and restore round-trips preserve piece positions, HP, territory ownership, credits,
cards, deck order, turn number, phase, and RNG seed, per 015_game_deployment.txt.

1.6.9. Deterministic Seeded Randomness
Identical seeds reproduce identical dice rolls and card draws across repeated runs, per
019_game_data_structures_algorithms.txt's seeded RNG service.

1.6.10. Post-Victory State Lock
No command (movement, attack, card play, upgrade purchase) may mutate state once a victory
condition has been reached; every such attempt is rejected without side effects.

1.7. Debug Panel (Development-Only)
1.7.1. Available only in development builds, never in a production/release build, per
015_game_deployment.txt build-configuration rules.
1.7.2. Capable of: changing the random seed; assigning credits; assigning cards; setting
piece HP; changing territory ownership; advancing phases; triggering each of the three
victory conditions directly; resetting the board.
1.7.3. Debug-panel actions bypass normal command validation by design (they exist to reach
test states quickly), but every debug-panel action is itself logged to the event log per
020_game_logging_standards.txt, distinguishably marked as a debug action.

1.8. Naming and Structure Conventions
1.8.1. Test modules mirror production module names 1:1 (`test_<module_name>.py`), per
006_game_scaffolding.txt Section 1.8.2.
1.8.2. Test function names state the scenario and expected outcome, e.g.
`test_bishop_orthogonal_move_is_illegal`, per
024_game_variable_func_class_decorator_exceptions_naming_conventions.txt.
