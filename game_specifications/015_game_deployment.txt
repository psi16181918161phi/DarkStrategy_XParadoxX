1.1. Abstract
This document specifies deployment build configurations and match-persistence behavior for
X Paradox X, including the distinction between development and production builds referenced
by 009_game_unit_tests.txt and 015's own role as the deployment target definition for the
LabLab AI Factory hackathon submission built on Natively AI.

1.2. Key Words
deployment, build configuration, persistence, autosave, New/Continue/Reset, Natively AI,
hackathon submission.

1.3. Executive Summary
X Paradox X ships as a Natively-AI-generated Python backend (this repository) paired with a
web-rendered UI per 004_game_menu_context_menus.txt. Two build configurations exist:
development (debug panel enabled, verbose logging) and production (debug panel disabled,
per 009_game_unit_tests.txt Section 1.7.1). Match state autosaves continuously and supports
New Game, Continue Game, and Reset Match flows.

1.4. Key Findings
1.4.1. This repository (DarkStrategy_XParadoxX) is confirmed, per explicit user direction,
to be the actual Python backend implementation target for the Natively AI hackathon
submission, not a throwaway planning artifact.
1.4.2. Exactly two build configurations are defined: development and production; the debug
panel (009_game_unit_tests.txt Section 1.7) is present only in development builds.
1.4.3. Persistence uses a local save file (format per 021_game_data_standards.txt) rather
than a networked database, consistent with the no-account, no-network MVP scope
(001_game_concept.txt Section 1.9.2).
1.4.4. Autosave triggers at the end of every completed turn (End Turn phase,
017_game_rules.txt Section 1.8), not merely on application exit, to minimize data loss.
1.4.5. Reset Match and Reset Session are distinct, explicit, user-confirmed actions
(004_game_menu_context_menus.txt Settings screen) that never fire implicitly.

1.5. Philosophical Preamble
Deployment is the point where every prior design promise either survives contact with a real
running build or does not. This document exists to make explicit what "shipped" means for a
hackathon-scale prototype: two build configurations, one persistence contract, and one
confirmed target platform.

1.7. Persistence and Autosave

1.7.1. Save Data Contents
Board size and layout, piece positions and HP, territory ownership and upgrades, each
player's credits and Dominion Points, each player's hand and remaining deck order, current
turn number and phase, RNG seed, and accumulated per-match/per-session statistics
(010_game_player_statistics.txt).

1.7.2. Save Triggers
Autosave fires at the end of every End Turn phase (017_game_rules.txt Section 1.8) and
immediately before application shutdown, if shutdown is detected gracefully.

1.7.3. New / Continue / Reset
1.7.3.1. New Game: initializes a fresh match at the player-selected board size
(017_game_rules.txt Section 1.6.1), discarding any prior autosave for that save slot only
after explicit confirmation.
1.7.3.2. Continue Game: restores the most recent autosave exactly, offered on the Main Menu
only when a valid autosave exists (004_game_menu_context_menus.txt Section 1.6.1).
1.7.3.3. Reset Match: explicit, user-confirmed action (two-step confirm per
004_game_menu_context_menus.txt Section 1.9) that discards the current match's state but
retains per-session statistics (010_game_player_statistics.txt Section 1.7).

1.8. Hackathon Submission Target (Natively AI)
1.8.1. This repository is the Python backend generated for and submitted to the LabLab AI
Factory hackathon via Natively AI, per explicit user confirmation during the 2026-07-30
clarification session.
1.8.2. The production build configuration (Section 1.6) is the configuration submitted for
hackathon judging.
1.8.3. No external paid services or accounts are required to run or judge the submission,
consistent with the no-network MVP scope.
