1.1. Abstract
This document is the authoritative parking lot for every feature, mechanic, or mode
explicitly excluded from the X Paradox X MVP (001_game_concept.txt Section 1.9.2), so that
good ideas are recorded rather than lost, and so that scope-creep requests during
implementation can be routed here instead of silently expanding the MVP.

1.2. Key Words
wishlist, deferred features, backlog, stretch goals, post-hackathon roadmap, scope discipline.

1.3. Executive Summary
Every item below was considered during the original ideation session or the 2026-07-30
documentation session and deliberately deferred, not rejected. Items are grouped into
deferred modes/features, deferred rules complexity, and deferred content expansion, each with
a one-line rationale for deferral.

1.4. Key Findings
1.4.1. Deferral is not deletion: every item here remains a candidate for a post-hackathon
roadmap and must be re-evaluated against 001_game_concept.txt Section 1.9 before being
promoted into an active specification document.
1.4.2. The largest deferred category is rules complexity that standard chess pieces
technically imply (check/checkmate nuance, castling, en passant) but that the MVP
simplifies away, per 017_game_rules.txt Section 1.15 Risk table.
1.4.3. Online multiplayer and user accounts are the most frequently repeated exclusion across
the corpus (001, 016) and are restated here as the canonical wishlist entries for that theme.
1.4.4. Any promotion of a wishlist item to active scope requires updating
001_game_concept.txt Section 1.9 and the relevant mechanics/mode document in the same change,
per the version-control discipline in 0000_documentation_standards.txt Section 1.6.7.

1.5. Philosophical Preamble
A wishlist is where ambition goes to wait its turn. Recording a deferred idea with its
rationale protects the vertical-slice-first design pillar (003_game_philosophy.txt Section
1.6.5) without pretending the idea was never worth having.

1.6. Deferred Modes and Features
| Item | Rationale for Deferral |
|------|---------------------------|
| Autonomous single-player AI opponent (beyond the advisory Oracle) | MVP only requires an advisory AI; a fully autonomous opponent is "only if time permits" per the original ideation session |
| Online/networked multiplayer | Explicitly out of MVP scope; requires backend infrastructure not needed for the hackathon demo |
| User accounts, profiles, authentication | Explicitly out of MVP scope per 001_game_concept.txt Section 1.9.2 |
| Ranked/competitive matchmaking | Depends on online multiplayer, itself deferred |
| Spectator mode | Not required for a two-player local pass-and-play MVP |
| Real-money economy or monetization | Explicitly excluded per the original ideation session's Core MVP boundaries |

1.7. Deferred Rules Complexity
| Item | Rationale for Deferral |
|------|---------------------------|
| Full chess check/checkmate legality nuance | 017_game_rules.txt uses King-capture-as-victory rather than checkmate to keep combat resolution dice-based and consistent across all pieces |
| Castling | Adds special-case movement logic not required for the MVP vertical slice |
| En passant | Adds special-case pawn-capture logic not required for the MVP vertical slice |
| Pawn promotion | Standard chess pawn promotion is not yet reconciled with the HP/Attack/Defence stat-block system (017_game_rules.txt Section 1.7.2); deferred pending design |
| Dominion Points threshold scaling formula for non-default board sizes | 017_game_rules.txt Section 1.11.3 flags this as a future balance revision rather than silently changing the default |

1.8. Deferred Content Expansion
| Item | Rationale for Deferral |
|------|---------------------------|
| Additional upgrade types beyond Fortress/Market/Relay | MVP ships the three upgrades carried forward from the original ideation session only |
| Additional victory conditions | MVP ships exactly the three defined in 017_game_rules.txt Section 1.11 |
| Alternate/variant board shapes (non-square) | User explicitly required the board to remain square at all supported sizes (017_game_rules.txt Section 1.6.1) |
| Bespoke custom-unit variant mode (Crown/Knight/Scout/Architect from the original ideation session) | Explicitly retained as a possible optional variant mode, not the primary canon, per 001_game_concept.txt Section 1.8 |
| Procedurally generated boards | Explicitly excluded per the original ideation session's Core MVP boundaries |

1.9. Explicit Non-Goals
1.9.1. X Paradox X will not implement open-ended, AI-generated rules during a live match; any
AI feature remains advisory-only per 016_game_modes.txt Section 1.7.3, permanently, not just
for the MVP.
1.9.2. X Paradox X will not silently expand its hallucination envelope beyond the ranges
declared in 017_game_rules.txt without a new, explicitly declared and reviewed envelope
invocation.
